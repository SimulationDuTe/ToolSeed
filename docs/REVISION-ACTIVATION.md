# 让经过实际检查的修订成为当前能力

2026-10-26，本地开发增量，未发布。接续[复用后更新](REUSE-UPDATES.md)：宿主提出候选修订后，
可以执行检查，通过后启用新版；失败保留旧版，并留下具体检查结果供后续修订使用。

## 宿主执行流程

DSH 插件增加可关闭的原生工具 `toolseed_validate_revision`。名称前缀随 `mcpServer` 配置变化，
开关为 `revisionValidation`，默认开启。Core MCP 仍为五个工具，其他宿主没有自动获得该原生入口。

1. 保存或学习修订时，返回 `revision_validation`，包含能力、候选版本、内容哈希和基础版本。
2. 模型用 `mode: inspect`、`binding: 返回的 revision_validation` 读取候选及之前失败的检查。
   这是验证材料，没有生成正常交付记录，也没有放开候选执行权限。
3. 模型根据改动、原方法和适用范围选择新场景与回归用例，用 `mode: validate` 提交。
   工具逐项通过 DSH 公共 `tools.execute` 执行，保留 agent 范围、宿主准入、取消和工具错误。
4. 执行器对实际结构化输出做断言。全部通过且基础版本未变时，Core 在同一事务中记录验证、
   晋升并切换当前版本。后续 `toolbox_run` 返回新版。失败则停止剩余检查，保存失败/跳过事实，旧版继续可用。

每个用例一次宿主工具调用，2–8 个用例，至少一个 `new` 和一个 `regression`。
每例有 1–8 条精确标量断言；路径用字符串数组，允许访问数组下标，例如 `["items", "0", "valid"]`。
用例应执行候选方法并检查结果；复杂流程可使用宿主已有的、获准的测试工具，不在 Core 增加代码执行器。
示例中的 `project_check` 是占位符，实际调用必须选择当前宿主可见的工具：

```json
{
  "mode": "validate",
  "binding": {
    "capability_id": "cap_实际值", "version_id": "ver_候选值",
    "content_hash": "sha256:实际值", "base_version_id": "ver_基础值"
  },
  "cases": [
    {"id": "changed-output", "role": "new", "purpose": "新输出条件符合修订约定",
     "tool": "project_check", "arguments": {"scenario": "changed"},
     "assertions": [{"path": ["output", "valid"], "equals": true}]},
    {"id": "original-output", "role": "regression", "purpose": "原来支持的场景仍然正确",
     "tool": "project_check", "arguments": {"scenario": "original"},
     "assertions": [{"path": ["output", "valid"], "equals": true}]}
  ]
}
```

## 结果如何保留和使用

- `revision_validated` 保存绑定、执行批次、计划哈希、用例用途、状态、失败断言下标和结果哈希。
  返回给宿主的 `diagnostics` 带有界的预期值、实际标量值和缺失/异常标记，便于判断失败原因；
  执行器不把这些值或原始参数、输出复制到长期能力库。哈希本身无法还原完整用例。
- 版本验证记录的来源为 `test_runner`，执行器根据真实返回生成结果，模型不能在这个工具里提交自述的 `passed`。
  模型仍负责选择覆盖范围。无关检查通过不证明方法有效，也不等于用户任务成功。
- 后续 `inspect` 返回最近一次检查摘要；旧版 `reuse_summary` 也带候选的验证摘要。
  失败断言仅证明所检查条件不成立，不自动推断根因或生成修复教训；模型可结合实际输出继续提炼。
- 重试同一收据幂等；同一批次不接受不同结果。之后发生回滚或归档时，重放旧收据不能重新启用新版。
- 内容审核、隔离、归档、精确哈希和当前基础版本门禁在执行前和提交时都检查。
  并发版本变化时返回冲突，保留现有状态。写入失败回滚验证记录与版本切换，避免半完成状态。
- 有基础版本记录的旧复用修订可以继续验证；无法确定来源版本的历史候选不会猜测基础版本，保留原管理流程。

执行器只允许固定的两个本地桥接操作 `prepare-revision-validation` / `complete-revision-validation`，
它们使用与 MCP 相同的 Python 和数据目录。管理 CLI 仍是可信本地调用边界，来源标签不提供密码学认证，
不能用来防御已经能任意调用本地管理接口的宿主。检查遵循已有授权，不授予额外权限。
每次工具检查设置 60 秒取消信号；取消或插件卸载后不继续检查、不提交晋升。
