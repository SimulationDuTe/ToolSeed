# Amended primary real-agent pilot (registered before its workers)

Baseline: HEAD c0cac122c1a149e3f6c1a2501a683db323fc5131, develop.

## Amendment and retention

The first feasibility batch in ../.test-data-agent-value executed six fresh agents
(three phase-0 A/B pairs). All six file-level outcomes passed the independent verifier,
but all three B workers reported a bridge startup ModuleNotFoundError for toolseed.
The project was visible from repository cwd but not actually installed in the venv.
No ToolSeed search reached Core, no capability was saved/delivered, and no adoption occurred.
Those runs are preserved as adverse treatment-availability evidence, not dropped or pooled
with the primary pilot. Their tokens and configuration repair labor are unknown, not zero.

Before this primary pilot, install the unchanged project normally into the same venv,
run the exact CLI bridge in a separate preflight directory/database, and require all four
APIs to work. Do not populate the primary B library during preflight. Then start a complete
new set of 18 fresh workers with new fixture copies and an empty B database. This is a
protocol/environment correction, not replacement of task failures to improve outcome rates.
Both arms use the corrected environment. Core, Schema, public protocol and existing
benchmark source remain unchanged.

## Frozen primary sample

Three local, reproducible domains, each initial + two later variants: environment config
launch, exact Decimal data conversion, Python behavior debugging. Nine pairs total.
Use identical paired inputs and acceptance contracts. Phase 0 precedes 1, which precedes 2.
Each task has a fresh non-forked child context; no model/provider override is selected.
Exact model identity/sampling/provider tokens are not exposed and remain unknown.
B uses current Skill and four actual LocalAdapter APIs via a logged optional CLI bridge;
no forced search/save/reuse and no hand-seeded procedure. Only B database persists across tasks.
A is prohibited from reading B or any external method library. Task-directory isolation is
instruction-based, not an OS security boundary; no cross-arm telemetry audit is available.

Task details and expected outputs are frozen by setup_pilot.py/spec.json before workers.
Immutable inputs are hashed; independent acceptance executes the real app, reruns converters,
and runs smoke + hidden debugging contracts. A worker success claim is not acceptance.
data2's nested JSON and debug2's mutable-default bug challenge narrow method applicability;
correct adaptation or declining a narrow procedure is allowed. Hard OS/tool rejection is not
covered and will not be claimed.

## Metrics and limits

Record Core save/search/delivery IDs and hashes, transport receipts/bytes/API time,
independent task result, and concise worker-reported opportunity/adoption/nonadoption.
Delivery is not adoption: report declared, task-bound delivery-linked use separately;
causal actual benefit is not independently observable from a method-read event.
Do not request/store chain-of-thought.

Timing markers are parent-before-launch to worker completion, including scheduling and
orchestration; they are not isolated model runtime and cannot establish speedup.
Unknowns: provider tokens, full Harness tool-operation count, fixed schema context cost,
model creation/validation/reflection cost and complete maintenance cost. API time excludes
interpreter startup; verification runtime is separate. Include all initial-task costs in
observed totals, not just follow-ups. Count feasibility/repair overhead separately. No positive
net-benefit claim when total costs cannot be measured. No significance/general learning claim
from nine dependent pairs. Do not run additional samples to seek favorable results.

Artifacts stay in ignored experiment directories; final report may be a formal Markdown
file. No Core/product/benchmark implementation edits, commits, pushes, tags or releases.
