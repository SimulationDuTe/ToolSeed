# ToolSeed 最终限范围跨任务复用验证：实验报告

日期：2026-10-21。产品基线 `c0cac122c1a149e3f6c1a2501a683db323fc5131`，分支 `develop`。
任务族：干净安装、外部工作目录与 MCP stdio 交付验收（T0 初始 + T1/T2/T3 变体）。
每组 1 初始 + 3 变体 = 8 次任务执行；两组工作区独立；B 组方法库跨任务保留。
数据见[逐任务表](final-per-task.csv)与[汇总](final-summary.json)。

## 0. 一句话结论

**8/8 任务由独立裁判通过；B 组出现了真实、完整、可核验的跨任务 Procedure 生命周期
（1 次保存 → 3 次检索交付 → 3 次实际采用），机制本身成立；但在本任务族上它没有带来
结果或成本优势——B 组反而多用 15% 的模型结算、16% 的请求 Token、8% 的工具调用和 24% 的
墙钟时间。净收益仍为 unknown，且受测量层 PARTIAL 状态与若干协议偏差限制。**

## 4. 是否出现真正的跨任务能力复用

**出现了，而且证据是客观的、可复核的，不只是 Agent 自述：**

- 交付与调用有带时间戳的收据（10 条，含 API 区间与响应字节），可归属到具体任务窗口；
- B 库终态有 3 条 `invocations` 记录；
- 三次采用各自写明应用了被交付 Procedure 的哪些步骤（2/8、8/9、4/8 步），且都在 T1/T2/T3
  的实际修复动作中留下对应产物；
- T1/T2/T3 都没有再次保存近似 Procedure——正是"库已有所需方法"才使重复外化被避免。

与上轮主试验（0 次保存、5 次空检索、0 次采用）相比，这是第一次观察到完整闭环。

**但"复用"并未转化为可测优势**：两组 8/8 全通过，没有结果差异；B 组在结算、Token、工具
调用和墙钟上都更高。因此本轮能支持的最强结论是：
**ToolSeed 的跨任务方法沉淀与再交付机制在真实 Agent 工作里可用；它是否值得，取决于被测
任务族是否有足够长的重复方法链，本族没有显示正收益。**

## 5. 现有证据支持的结论及其限制

支持的结论：

1. 交付链路可信：干净安装、外部 cwd、显式数据目录、含空格/中文路径四种形态下，
   真实 MCP stdio 握手均列出且只列出四个产品工具并返回结构化 stats。
2. 独立验收可自动化，不依赖 Agent 自评；两组同条件可比。
3. 跨任务 Procedure 的"保存—检索—交付—采用—免重复保存"链路在真实工作中跑通。
4. 方法库与被测软件状态可分离（A 组零调用、默认 `~/.toolseed` 未生成、各数据目录互不混用）。

限制（必须随结论一起引用）：

1. **测量层仍为 PARTIAL**：provider 计费 Token、失败/取消用量、物理请求与传输回退不可得；
   23 次失败尝试在记录中同样为零值，不能解释为免费。
2. **样本极小且结构化**：8 个任务、9 个能力中只有 1 个被保存并复用；每组仅 4 个任务且互相
   依赖，无法做显著性或总体推断。
3. **执行顺序不是随机化**：B→A 与 A→B 交替，且同一主机串行执行；T1 的失败次数差异使该阶段
   的成本对比不可归因。
4. **协议偏差**：T1-A 工人读取并执行了实验自身的驱动与裁判脚本（`judge_task.py`、
   `capture_task.py`、`aggregate_final.py`、`prepare_tasks.py`、`set_phase.py`），
   该组该任务未盲；我随后独立复跑了全部 8 个裁判，但盲性缺陷已存在，无法事后消除。
5. **夹具缺陷（非产品缺陷）**：我提供的 `check_delivery.py` 在缺少 `--expect-origin` 时会抛
   `AttributeError`，A、B 两组都真实踩到并各自绕过；产品代码未受影响。
6. **采用的自报成分**："采用了哪几条断言"来自 Agent 报告，我核对了收据里的交付事实，
   但没有独立判定"若无该 Procedure 结果是否更差"。
7. 沙箱环境差异：本机以 0700 权限创建的目录不可写，导致标准库临时目录与 `python -m venv`
   不可用；实际安装走 `uv` + 工作区缓存。此为环境事实，不影响产品结论，但会写入任何复现说明。

## 6. 最终产品建议

**建议：针对明确缺口做一次小改进，随后按新的预注册再决定是否继续；不建议按本轮形态继续
扩大实验，也不建议就此完全停止。**

理由：机制已被证明可用（这是此前从未有过的证据），但本族没有显示正收益，且收益能否测量
仍被 PARTIAL 测量层卡住。继续重复同一形态的 8 任务实验不会改变结论。

一次小改进的明确范围（只做一件可验证的事）：

1. **给"避免重复外化"补可核验证据**：在 Skill 的采用报告里强制区分"因为库里有而免于重新
   推导"与"库里有但仍然重做"，并让 Core 记录一次 `evidence_event`；当前证据只能看到
   "没有再保存"，看不到"省下了什么"。
2. **在成本侧补齐可判定性**：先取得 provider 侧的请求/用量窄字段（按上一轮结论所需字段
   清单），使"方法库路径的净成本"可判定；在此之前不宣称正收益。
3. **收窄适用族**：把方法库的价值主张限定在"方法链长、重复率高"的交付支持族
   （如多次发布/多环境验收矩阵），并在下一轮预注册里写明"每组至少 3 次同类方法外化"，
   否则本轮这类一次一方法的族无法摊薄外化成本。
4. 不改 Core 的存储、协议与四工具语义；不扩大产品范围；不把本轮的免费路由结果当作
   成本优势。
