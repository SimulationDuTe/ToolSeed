# 两轮真实任务：经验沉淀与跨会话复用

2026-10-27，这次观察到了完整闭环：**真实模型修复任务 A → 自主保存方法 → 新会话自动召回 →
实际使用方法修复任务 B → 使用观察回到同一能力**。两项任务的外部检查各 10 个案例通过，
测试库最终只有 1 个能力、1 个版本和 1 次完整方法交付。

## 实际发生了什么

| 阶段 | 证据 | 结果 |
|---|---|---|
| A 修复配置解析器 | 模型读取实现、执行失败基线、修改代码、增加回归，并实际运行 unittest | 本地 8 个测试方法通过；外部 10 案例通过，受保护输入不变 |
| A 提炼经验 | 自行加载 ToolSeed Skill、调用 search，再调用 learn | `learning_action: created`；保存 `procedure` 方法，包含适用条件、排查/修复方法、验证检查和边界 |
| B 开始 | 全新 Agent、独立宿主状态目录和另一套项目代码，只共用测试能力库 | 召回检索命中 1 个候选，提示被宿主正式提交到正常步骤 |
| B 读取并采用 | 模型自主调用 `toolbox_run`，随后修复另一实现并加入相应回归 | 完整方法在修复前交付；B 的代码与测试落实了方法中的检查，外部 10 案例通过 |
| B 回流观察 | 模型调用 `toolbox_learn`，绑定实际交付的版本、哈希与 invocation | `application: applied`、`learning_action: observation_added`；没有重复创建能力或版本 |

业务提示只有普通修复要求，没有出现 ToolSeed、能力 ID、保存经验或检索记忆的要求。
两轮都使用已安装的 DSH 0.2.1-rc.2 headless 与订阅接入 `openai-codex`，选择 `gpt-6.1-sol`。
学习、召回及更新模块从实际安装目录加载，不使用脚本化模型。

## 沉淀的内容

能力名：**Repair ordered configuration merges with explicit-value semantics**。
完整正文见 [capability.md](capability.md)，结构化证据见 [result.json](result.json)。

它保存的是可迁移的方法：先核对覆盖顺序和本地合同，区分缺失与显式假值，仅在字典双方均成立时递归合并，
其余值整体替换并深复制；再检查空字典、跨类型转换、已丢弃键重新出现，以及嵌套引用隔离。
同时排除了数组拼接、删除标记、反向优先级等不同语义的场景。修复脚本留在任务项目中，不是能力正文。

B 的使用观察具体记录了采用的步骤和实际检查，回到 A 的原能力：

- 能力：`cap_8c7420327d89`
- 版本：`ver_1880c29d70df`
- 交付：`inv_b39033bcfea7`
- 使用反馈：`ev_194d04f7be9e`

这次没有值得另起版本的方法变化，模型只追加观察，符合避免重复积累的目标。

## 验证范围与运行中修正

这是两项构造的真实模型修复任务，验证的是安装后机制在受控任务中的实际行为，不是运行中的 Desktop UI 会话验收，
也没有足够样本证明普遍成功率或净节省。两轮耗时分别约 414 秒和 161 秒，任务不同且存在缓存等因素，不能据此计算复用收益。

外部检查由确定性程序完成，另有自检确认原始错误会失败、正确参考实现通过、修改受保护输入会失败。
过程发现并修正了校验器在 Windows 路径分隔符下遗漏受保护文件检查的问题；正式 A/B 均使用修正后的检查。
模型的使用反馈仍标注为 `agent` 来源；外部结果没有被伪写成 Core 的任务成功信号。

启动阶段曾有两次失败，均保留证据：

1. Codex 插件异步刷新模型目录，而隔离会话立即请求，导致 `UNKNOWN_MODEL`。账号实际上已登录。
   测试接线增加有界的目录就绪等待后，正常取得 `gpt-6.1-sol` 并完成两轮。
2. 中途尝试现有 DeepSeek 官方 API 接入返回 401，没有执行任务工具；最终没有用它完成任务。

这些失败不计入真实模型的学习成功或失败。最终沿用已有登录，未执行退出或重新登录；没有复制登录令牌，也没有更改日常默认模型。
两轮使用独立工作目录、独立会话状态和一个空白测试能力库，没有预置或人工代存能力。
