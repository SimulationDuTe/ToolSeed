## 1. 研究问题与任务族选择

问题：在两组都可正常保留并复用项目脚本、文档、测试和配置的条件下，额外提供当前 ToolSeed
四工具及 Skill，能否自发形成 Procedure，供新任务实际采用，并在计入初始投入后改善结果或成本？

条件首选：**干净安装、外部工作目录与 MCP stdio 交付验收/诊断**。
理由是实际 CI 与交付脚本已有重复工作需求，且上轮确有外部目录导入失败；方法包含解释器、
安装来源、依赖、入口及子进程环境的判断，不只是固定格式转换或两行代码修复。
机械检查仍应优先用已有脚本自动化，不为突出 Procedure 而移除常规复用手段。

真实性界限：不是四起生产事故，也没有声称四个新版本已排期。
四个任务拟为当前实际管线的受控验收、依赖负例、已有错误回放与支持路径变体。
如果审查要求四个真实在途请求而非这种受控复现，则当前没有足够已确认任务，不开始执行。

### A 不使用 ToolSeed 的具体含义：须先批准

本任务族的共同裁判要验证 ToolSeed **被测软件**，会列举四工具并调用 stats。
这与 B 的 **Agent 方法库**是两个用途：

- A 不注册/调用用于解决任务的 ToolSeed 方法库，不读 B 数据库或 Procedure。
- A/B 均可执行相同被测包验收。其 MCP 调用标注 `scope=SUT-validation`，用独立临时测试目录。
- B 的可选方法库标注 `scope=agent-memory`，使用另一固定数据库；只有这里的保存/交付进入复用链路。
- 共同测试内部若使用 fixture Procedure，不算 Agent 自主保存、交付或采用，更不能进入 B 库。
  当前[package smoke](../../../scripts/package_smoke.py#L86-L104)本身只枚举工具并调用 stats。
- 若“A 不使用”连共同裁判对被测包的调用也不允许，该候选不合格；不能默默放宽 A 条件。

## 2. A/B 环境、普通工件保留与上下文

建议规模固定为 **每组 T0 初始任务 + T1/T2/T3 三个变体，共 8 次正式任务**。
无论 T0 是否保存，都按冻结计划观察后续任务，不因无保存而补种、换任务或加样本。

| 项目 | A | B |
|---|---|---|
| 初始项目 | 同一基线的独立副本 | 相同基线的另一副本 |
| 普通脚本/文档/测试/配置/工作目录 | 可创建、修改、保留、复用 | 完全相同 |
| 上一个任务的普通工件 | 不清空、不重置 | 不清空、不重置 |
| Agent 任务上下文 | 每任务新 session，零继承事件 | 相同 |
| 可选方法库 | 不注册、不使用 | 当前四工具和实际交付 Skill |
| 方法库初始状态 | 无 | 新目录、能力/版本/历史均为空，跨四任务保留 |
| 任务及独立验收 | 配对一致 | 配对一致 |

具体策略：

1. 两组各有持久项目根、运行目标目录和输出目录；不在生产工作树中执行。
   每阶段只投放该阶段冻结输入，不删除前阶段代码、runbook、测试、配置或环境。
2. 新 session 不 fork、不继承上一对话或隐藏会话摘要；可以读取本组已有项目工件。
   明确告诉两组共有四个验收任务、后面三个有相关变体，但不提前透露变体根因或期望修复。
3. 各组可编辑正常项目工件；外置裁判、固定供应 wheel 与可信期望独立只读。
   修改项目内脚本或测试不等于修改外置验收器，也不自动算不合规。
4. 项目中的产品 Core 不作为待改对象；本族只修环境、安装、启动配置及诊断/验证工件。
5. 旧九个未跟踪文件保持原位，不纳入新的组间共享可写目录，也不将旧实验解答当作 B 种子。
   如需错误回放，只在批准后向两组投放相同的脱敏错误证据。
6. B 的方法库、SUT 的测试数据库、A/B 普通输出、裁判证据目录使用不同明确路径。
   每次 MCP 启动显式指定数据目录，不触碰用户默认共享库。
7. 目录/权限配置需证明不会读取对组工件；cwd 可切换不等于权限隔离。
   若只能做软隔离，须在批准前明确接受该局限，保留完整工具账本并检查越界。
8. 不在案例之间手工复制 A/B 的解法，不给 B 额外人工提示，也不人工保存或推广版本。
9. 默认仅提供共同文件/终端工具，B 加四个 ToolSeed 工具。若需委派，先证明子会话模型与
   全量用量均可追踪；否则两组一致不启用委派，不能让成本流到未计量子会话。

执行顺序预定为 T0 A→B，T1 B→A，T2 A→B，T3 B→A；一对完成后再投放下一阶段。
不并行占用同一主机进行两组测量，减少争用；这不是随机化或盲法试验。
两组相同基础权限、工具版本、wheelhouse、缓存政策和任务预算；provider 缓存用量如实计费。
不能只清空 A 缓存，或通过删脚本/文档让 A 刻意从零开始。

## 3. 四个任务规格与独立验收

### 共同供应及产物

批准后从指定基线一次性准备相同 wheel、依赖锁和所需 Python 3.11/3.13 包，记录全部哈希。
目前构建目录的 0.3.0 工件不能使用。允许准备本地只读 wheelhouse，不在正式任务中靠不受控下载
引入版本漂移。准备成本单列记录，不暗中摊到零；本轮没有准备这些环境。

每个任务的 Agent 输出包括可重跑的验收入口/命令、结构化结果及必要的普通项目工件。
不要求必须写新脚本；已有检查已足够时可直接复用。
下面根因及裁判细节在正式执行时属于评估端规格，不当作 Agent 的答案提示。

| 任务 | 输入与变化 | 必须独立成立的目标 | 真实性类型 |
|---|---|---|---|
| T0 初始：正常干净安装与验收 | 固定 wheel、普通外部 cwd、Python 3.11、新目标环境 | 非 editable 安装；来源不在源码树；Skill、入口、MCP 四工具及结构化 stats 合格；产物可重跑 | 现有 CI/交付流程的基准验收 |
| T1 依赖缺失诊断 | 新 Python 3.13 目标；被测包存在但所需 SDK 依赖缺失；前工件完整保留 | 先记录实际诊断，再在指定目标持久修复依赖；清洗环境后独立子进程通过；不得靠父进程路径注入 | 依据真实依赖要求与缺 SDK 用例设计的负例，不称历史生产事故 |
| T2 外部 cwd 导入错误回放 | 新目标已有依赖，但项目仅能借源码 cwd 导入，未正确安装被测包 | 外部工作目录、清除 PYTHONPATH/PYTHONHOME 后安装来源正确、四工具与 stats 合格 | 对上轮 ModuleNotFoundError 的受控回放，不声称完全重建旧宿主状态 |
| T3 路径/入口变体 | Python 3.13；带空格和中文的目标/工作目录；独立指定数据目录；不预置故障 | 绝对入口/解释器配置正确；真实 stdio 握手、四工具及 stats 通过；导入来源及数据目录无串组 | 支持路径验收，不虚构既有事故 |

T1/T2 环境初始化只创建新的任务输入目标，不能覆盖本组已有普通工件；不重放权限拒绝故障，
因为其根因未确定且权限修复会混杂处理条件。T3 是无预置故障的适用变体，不能硬凑一次失败。

### 独立裁判

优先复用只读的[包 smoke](../../../scripts/package_smoke.py)和
[干净安装检查](../../../scripts/verify_release.py)的既有能力。
如需要结构化输出或路径参数，只批准实验专用薄包装，不另造通用运行器或改产品脚本。
包装与输入清单须在正式样本前冻结；**当前未实现或运行它们**。

裁判至少检查：

- 供应 wheel SHA 与基线构建清单一致；实际目标环境中的安装文件和 Skill 指纹可核对。
- 包来源不在源码目录，不用 editable、父 cwd、PYTHONPATH 或额外影子模块冒充安装成功。
- 清理环境后的真实子进程返回码、模块来源、元数据版本、入口与帮助命令。
- 官方 MCP stdio 真实列出且只列出四工具，stats 返回结构化数据；指定数据目录互不混用。
- 不以 skip、Agent 自称成功、修改项目内测试或伪造输出替代裁判结果。
- 冻结输入/裁判未变；任务结束快照中的代码、普通工件、输出及库状态可追溯。

共同 SUT 验收费用计入两组相应验证成本；其调用不计入 Agent 记忆库的搜索/保存/采用。

## 4. 指标、来源与采用判断

### 4.1 每任务记录

| 指标 | 证据来源/口径 |
|---|---|
| 完成结果 | 外置裁判结果、退出码、实际输出及哈希；保留失败、超时、未完成、基础设施中断状态 |
| 复用机会识别 | 两组相同的简短终稿字段及实际创建方法工件的行为；缺失为 unknown，不额外开模型轮追问 |
| 普通工件创建/复用 | 任务前后快照、文件 diff/hash、read/execute 事件及后续实际使用位置；存在文件不等于复用 |
| 保存尝试/成功 | 仅 B agent-memory 原始调用/响应；能力 ID、版本、状态与正文指纹；accepted 不等于正确性验证 |
| 检索 | query/context、结果卡及其 ID/版本、错误/空结果，区分工具接入失败与正常空列表 |
| 读取/交付 | 实际 toolbox_run 调用和响应、Invocation、版本及正文哈希，不把检索卡当正文读取 |
| 跨任务版本使用 | 早于新任务创建的已保存版本、该任务实际获得的版本/正文及应用行为链 |
| Token/模型请求 | 每次原始请求/尝试、解析后模型、输入/输出及可得缓存/推理 Token；重试/失败/取消不丢弃 |
| 工具/重试/中断 | 全部工具 call/result（含参数、输出或可取回附件）、错误、退出码、时间、缺失配对、重试原因 |
| 时间/费用 | 墙钟、可观测模型/工具活动区间、批准等待、超时、中断；可获得账单/定价映射；不可得即 unknown |

只保存任务输入、可公开输出、工具证据及计量元数据；不要求或公开隐藏推理、私有系统提示和
认证材料。固定系统/工具配置可用版本/哈希核对，Token 仍由 provider 的完整输入用量计入。
完整工具账本不能被 raw 字段截断或 UI 摘要替代；敏感参数须安全脱敏并标明缺口。

### 4.2 保存版本与实际采用的分层

1. **保存**：真实响应和只读库快照可对应 capability_id/version_id、正文 hash、状态、时间。
   缺少既有响应字段时在实验层计算/核对，不扩展四工具 Schema。
2. **跨任务交付**：保存早于该新任务开始，工具实际返回了对应可交付版本。
   同任务保存后读回只算任务内行为，不算跨任务复用。
3. **自报应用**：Agent 简短报告引用 Invocation/版本及应用位置，不要求链式思考。
4. **可审计应用**：交付后的诊断、命令或项目改动与该版本的具体方法一致，有工件/工具事件佐证。
   仅顺序相邻、内容相似或自称采用不够；含糊/矛盾标 unknown/disputed。
5. **目标通过**：独立裁判通过。仍不等于 Procedure 导致改善；与 A 的完整成本作描述性比较。

若方法只从本组普通 runbook/脚本取得，归入常规工件复用；不能因为 B 曾保存同类内容就归因于
ToolSeed。若声称经 ToolSeed 交付后缓存为普通工件再复用，必须追溯原始交付版本与缓存哈希；
与“先写项目文档，再同文保存进库”的情况分开报告，不能双算收益。

新候选版本仍遵守当前产品门禁；不人工推广、改状态或用管理 API 解锁它来制造后续采用。
默认只在独立实验记录保存验收结果，不向 Core 注入模拟成功或为统计补写结果。

### 4.3 预定解释

| 观察 | 解释与允许的检查 |
|---|---|
| 无保存 | 没有检验到已保存能力的后续复用；不强迫保存、不追加样本 |
| 已保存但不可交付 | 先区分结构/状态门禁与质量验证，不能说已经有可用方法 |
| 已有可用版本但未检索到 | 核对是否实际搜索、query/context/适用性与卡片；没有搜索不算检索召回失败 |
| 检索到但未采用 | 区分未读取、读取未应用；检查质量、边界及采用成本，不把拒绝一概视为错误 |
| 实际采用但无收益 | 检查工作是否真的减少，以及是否只是重复 A 的普通脚本；保留负/零结果 |
| 采用后观察到收益 | 仍扣初始创建、验证、配置、读取和维护成本，限于本四任务观察窗口 |
| 数据或成本不足 | unknown；已知零次调用可以记 0，未知用量/费用不能记 0 |

## 5. 成本口径与增量判断

### 总量优先，分阶段不强行分摊

为 A/B 分别记初始配置 S、四个任务的全部模型/工具/自测成本 C、独立验证 V、窗口内维护 M：

`Total_A = S_A + Σ(C_A,T0..T3) + V_A + M_A`

`Total_B = S_B + Σ(C_B,T0..T3) + V_B + M_B`

每个可比单位的观察节省为 `Total_A - Total_B`。Token、调用、时间、货币分别报告，
不把它们任意加成一个分数。共同研究准备成本另列并说明共享分配，不悄悄归零。
ToolSeed 的额外启动/配置/工具 schema/Skill 暴露、创建、验证、搜索、正文读取、修订等全部留在 B 总量。
A 的普通脚本/runbook 创建、验证、维护同样全部留在 A 总量。

- 所有模型请求均计，包括初始规划、形成 Procedure、验证、重试、压缩/总结、读取及失败。
- Token 必须来自 provider 原始 usage；对输入总量/未缓存输入/缓存读写的映射先审定，避免重复加算。
  缺失、provider 不支持、明确为零分别编码；不用字符/4、上下文压力值或字节数冒充计费 Token。
- 费用有合法价格或实际账单映射才计算，记录币种、价格生效日期、缓存费率和实际路由。
  订阅不可按次计价时货币净收益 unknown，不宣称每次免费。
- 分阶段标签依据可观察事件：创建、方法验证、检索、读取、维护/适配、普通工件操作。
  混合模型轮不能精确拆 Token 时，阶段分项为 unknown，但完整任务总量仍保留；不重复记账。
- 验证费用含 Agent 自测与父裁判；共同测试内部的 ToolSeed 调用作为 SUT 验证，不当作方法库采用。
- 活动时间以原始请求/工具/子进程区间核对。并行区间用并集或分轨报告，不盲加；
  未结束/取消区间注明下界及未知尾部，不从 sessionStats 的零值推断没有耗时。
- 模型 API 墙钟不是 CPU 活跃时间；SDK/server 存活时间也不是 CPU 成本。排队、人工等待和中断分别记录。
- 成本窗口是这四个任务及其必要前期配置，不能丢掉 T0，只汇报后续节省，也不推算虚构未来摊销次数。
  长期维护尚未发生就说明未测；只有实际观察到的窗口内维护计入本轮。

### 判断规则

任务通过数、有效配对、成本完整性和采用链路分别报告，不用“成功任务平均成本”丢掉失败成本。
只有任务结果不劣、跨任务实际应用链路成立，且相应成本总量可比完整时，才可说这个小窗口
观察到某单位的节省。货币缺失不影响已完整的 Token 描述，但不支持货币净收益结论。
若一个完整成本维度减少而其他维度变差，报告权衡，不笼统称净收益为正。

单个任务族、四对任务只检验行为链路与成本测量是否成立；不作显著性、普遍因果、跨领域泛化
或“自主学习能力增长”结论。即使四次结果都通过，也不等于 ToolSeed 有收益。

## 6. 冻结、风险与停止条件

### 正式请求前唯一冻结附件（当前均未齐备）

- 选定 provider/请求与解析后模型标识、adapter/profile 版本；所有可配置采样及 reasoning/maxTokens
  参数和默认行为。无法设置的字段明确 not_supported，不伪称固定 seed。
- 现成启动入口、身份凭据安全注入方式（不记录密钥）、完整 JSONL 输出及每尝试 usage 样例。
- 两组工具/权限/cwd/缓存/网络政策；B 四工具 schema 与 Skill 的准确指纹；正常工具对两组一致。
- 固定 wheel 和依赖/主机/解释器清单、八份任务输入、裁判实现/期望及哈希。
